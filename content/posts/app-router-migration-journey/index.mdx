## Part 1: The Build Error Crisis

### The Problem

```bash
Module build failed: UnhandledSchemeError: Reading from "node:fs" is not handled by plugins
Import trace:
node:fs
./src/lib/contentLoader.ts
./src/components/Portfolio.tsx
```

### Root Cause Analysis

The error revealed a fundamental misunderstanding of **Server vs Client Component boundaries** in Next.js 13+.

```tsx
// ❌ PROBLEM: This chain crosses boundaries incorrectly

// Portfolio.tsx (in /src/components/)
import { loadAllProjects } from '../lib/contentLoader';
// ↓
// contentLoader.ts
import fs from 'node:fs';
import path from 'node:path';
// ↓
// Webpack tries to bundle fs/path for browser ❌
```

**Why This Fails:**

1. Pages Router bundles everything for both server AND client
2. Webpack can't determine what's server-only
3. Node.js modules (`fs`, `path`) can't run in browsers
4. Build crashes

### The Solution: App Router Server Components

```tsx
// ✅ SOLUTION: App Router with proper boundaries

// app/page.tsx (Server Component by default)
const projects = loadAllProjects(); // ✅ fs/path OK here!
const enriched = enrichProjectsWithTechnologies(projects, technologies);

// Pass data across boundary as JSON
<PortfolioClient projects={enriched} />;
```

**Key Insight:** The `'use client'` directive creates a **bundling boundary**. Everything above it can use Node.js APIs. Everything below it must be browser-safe.

## Part 2: Data Enrichment Architecture

### The Challenge

Our content is **normalized** (relational):

\`\`\`yaml

# projects/devcon.mdx

technologies: ['react', 'node', 'express', 'mongodb'] # Just slugs
\`\`\`

But our UI needs **denormalized** (embedded) data:

\`\`\`tsx

<TechBadge>
  <img src={tech.logo} /> {/* Need full object! */}
  <span>{tech.name}</span>
</TechBadge>
\`\`\`

### The Enrichment Pattern

```typescript
// Step 1: Define enriched type
export interface EnrichedProject extends Omit<Project, 'technologySlugs'> {
  technologies: Technology[]; // Full objects, not slugs
}

// Step 2: Create enrichment function
export function enrichProjectsWithTechnologies(
  projects: Project[],
  technologies: Technology[]
): EnrichedProject[] {
  // O(1) lookup using Map
  const techMap = new Map(technologies.map((tech) => [tech.slug, tech]));

  return projects.map((project) => {
    const technologies = project.technologySlugs
      .map((slug) => techMap.get(slug))
      .filter((tech): tech is Technology => tech !== undefined);

    const { technologySlugs, ...rest } = project;
    return { ...rest, technologies };
  });
}
```

**Performance Analysis:**

- **Without Map (O(n×m))**: 4 projects × 9 technologies = 36 lookups
- **With Map (O(n+m))**: 4 + 9 = 13 operations
- **At scale (100×50)**: 5000 vs 150 operations 🔥

### Why This Matters

This pattern mirrors **Entity Framework** (C#) or **Prisma** (TypeScript) ORM patterns:

```csharp
// C# Entity Framework equivalent
var projects = db.Projects
  .Include(p => p.Technologies)  // Eager loading
  .ToList();
```

Our enrichment function IS the `Include()` for static files!

## Part 3: The Three-Tier Content Architecture

### Architectural Design

```
┌─────────────────────────────────────────┐
│   Tier 1: Technologies (Taxonomy)       │
│   - Foundational entities               │
│   - slug, name, logo                    │
└─────────────────┬───────────────────────┘
                  │ referenced by
┌─────────────────▼───────────────────────┐
│   Tier 2: Projects (Content)            │
│   - Uses technologies                   │
│   - technologySlugs → enriched          │
└─────────────────┬───────────────────────┘
                  │ referenced by
┌─────────────────▼───────────────────────┐
│   Tier 3: Posts (Content)               │
│   - References technologies & projects  │
│   - Enables "Related Content"           │
└─────────────────────────────────────────┘
```

### Real-World Parallels

| Your Architecture | E-Commerce | Netflix    | LinkedIn     |
| ----------------- | ---------- | ---------- | ------------ |
| Technologies      | Categories | Genres     | Skills       |
| Projects          | Products   | Movies     | Experience   |
| Posts             | Reviews    | User Lists | Endorsements |

### Implementation

```typescript
// 1. Load Technologies
const technologies = loadAllTechnologies();
// → [{ slug: 'react', name: 'React', logo: '/logos/react.svg' }, ...]

// 2. Load Projects
const projects = loadAllProjects();
// → [{ slug: 'devcon', technologySlugs: ['react', 'node'] }, ...]

// 3. Enrich

// → [{ slug: 'devcon', technologies: [<Technology>, <Technology>] }, ...]

// 4. Render

    <Card>

        <Badge>

        </Badge>
      ))}

  ));
}
```

## Part 4: Server/Client Component Composition

### The Pattern

```tsx
// ╔══════════════════════════════════════╗
// ║     SERVER COMPONENT (Portfolio)     ║
// ╚══════════════════════════════════════╝

async function Portfolio() {
  // ✅ Node.js APIs OK here
  const projects = loadAllProjects();
  const technologies = loadAllTechnologies();
  const enriched = enrichProjectsWithTechnologies(projects, technologies);

  // Pass data across boundary ↓
  return <PortfolioClient projects={enriched} />;
}

// ╔══════════════════════════════════════╗
// ║    CLIENT COMPONENT (PortfolioClient)║
// ╚══════════════════════════════════════╝

('use client');

function PortfolioClient({ projects }: { projects: EnrichedProject[] }) {
  // ✅ React hooks OK here
  const [selected, setSelected] = useState<EnrichedProject | null>(null);

  return (
    <>
      {projects.map((project) => (
        <Card onClick={() => setSelected(project)}>{/* Interactive! */}</Card>
      ))}

      {selected && (
        <Modal project={selected} onClose={() => setSelected(null)} />
      )}
    </>
  );
}
```

### Why This Architecture Wins

**Bundle Size Impact:**

| Component           | Pages Router                              | App Router            |
| ------------------- | ----------------------------------------- | --------------------- |
| Portfolio.tsx       | ~100KB (includes fs, path, contentLoader) | ~0KB (server-only)    |
| PortfolioClient.tsx | Included above                            | ~15KB (just UI logic) |
| **Total**           | ~100KB                                    | ~15KB                 |

**85KB savings** on this component alone!

**SEO Impact:**

```html
<!-- Server Component renders real HTML -->
<div class="portfolio_item">
  <h3>DevCon</h3>
  <span>React</span>
  <span>Node.js</span>
</div>

<!-- Not this: -->
<div id="root"></div>
<script>
  // Wait for JS to load, then render...
</script>
```

Crawlers see content immediately. Lighthouse loves this.

## Part 6: Modal Implementation with useState

### The Challenge

Modal requires:

1. State management (which project is selected?)
2. Event handling (onClick to open)
3. Conditional rendering (show/hide)

All three require **Client Components**.

### The Solution

```typescript
'use client';

import { useState } from 'react';

function PortfolioClient({ projects }: { projects: EnrichedProject[] }) {
  // 1. State Management
  const [selectedProject, setSelectedProject] =
    useState<EnrichedProject | null>(null);

  // 2. Event Handlers
  const handleOpenModal = (project: EnrichedProject) => {
    setSelectedProject(project);
  };

  const handleCloseModal = () => {
    setSelectedProject(null);
  };

  return (
    <>
      {/* Cards with onClick */}
      {projects.map((project) => (
        <Card onClick={() => handleOpenModal(project)}>{project.name}</Card>
      ))}

      {/* 3. Conditional Rendering */}
      {selectedProject && (
        <PortfolioModalbox value={selectedProject} close={handleCloseModal} />
      )}
    </>
  );
}
```

### State Flow Diagram

```
┌─────────────────────────────────────┐
│  Initial State: selectedProject = null │
└─────────────────────────────────────┘
              │
              │ User clicks card
              ▼
┌─────────────────────────────────────┐
│  handleOpenModal(project)           │
│  → setSelectedProject(project)      │
└─────────────────────────────────────┘
              │
              │ State updates
              ▼
┌─────────────────────────────────────┐
│  Component re-renders               │
│  selectedProject !== null           │
│  → Modal appears!                   │
└─────────────────────────────────────┘
              │
              │ User clicks close
              ▼
┌─────────────────────────────────────┐
│  handleCloseModal()                 │
│  → setSelectedProject(null)         │
└─────────────────────────────────────┘
              │
              │ State updates
              ▼
┌─────────────────────────────────────┐
│  Component re-renders               │
│  selectedProject === null           │
│  → Modal disappears!                │
└─────────────────────────────────────┘
```

## Part 7: Performance Optimization Strategies

### Current Architecture Performance

**Static Site Generation (SSG):**

\`\`\`bash
Build Time: ~15s
First Load JS: ~150KB
Time to Interactive: <1s
Lighthouse Score: 90+ (achievable)
\`\`\`

**How It Works:**

```tsx
// This function runs at BUILD TIME, not request time
async function Portfolio() {
  const projects = loadAllProjects(); // Reads files ONCE during build
  return <PortfolioClient projects={projects} />;
}
```

Next.js generates this HTML file:

```html
<!-- public/index.html -->
<div class="portfolio">
  <div class="card">DevCon</div>
  <div class="card">B&B Real Estate</div>
  <!-- All data pre-rendered! -->
</div>
<script src="/_next/static/chunks/portfolio-client.js"></script>
```

**Comparison:**

| Approach      | HTML Generation | Data Fetch   | JS Required |
| ------------- | --------------- | ------------ | ----------- |
| **SSG (You)** | Build time      | Build time   | UI only     |
| **SSR**       | Request time    | Request time | UI only     |
| **CSR**       | None            | Runtime      | Everything  |

### Bundle Size Breakdown

```
Total: ~150KB

Framework:
  ├─ React: ~50KB
  ├─ Next.js Router: ~30KB
  └─ Swiper: ~25KB

Your Code:
  ├─ PortfolioClient: ~10KB
  ├─ PortfolioModalbox: ~8KB
  ├─ Icons: ~5KB
  └─ Other components: ~22KB
```

### Optimization Opportunities

**1. Dynamic Imports (Code Splitting)**

\`\`\`typescript
import dynamic from 'next/dynamic';

const PortfolioModalbox = dynamic(
() => import('./PortfolioModalbox'),
{ ssr: false } // Only load when needed
);
\`\`\`

**Savings:** ~8KB not loaded until modal opens

**2. Image Optimization**

\`\`\`tsx
import Image from 'next/image';

<Image
  src={project.image}
  width={800}
  height={600}
  alt={project.name}
  loading='lazy'
  placeholder='blur'
/>
\`\`\`

**Benefits:**

- Automatic WebP/AVIF conversion
- Lazy loading built-in
- Blur placeholder during load
- Responsive srcset

**3. Remove Unused Libraries**

Check if you actually need:

- jQuery (if still present)
- Lodash (use native JS)
- Moment.js (use date-fns or native)

## Part 10: Interview Preparation

### Questions You Can Now Answer

**Q: "What's the difference between Server and Client Components?"**

**A:** "Server Components run on the server during build or request time and can access Node.js APIs like filesystem and databases. They reduce bundle size because component code doesn't ship to the browser. Client Components run in the browser and handle interactivity using React hooks and event handlers. You mark them with 'use client'.

In my portfolio, I use Server Components to fetch and enrich project data from MDX files using Node.js fs module, then pass that data to Client Components that manage modal state and user interactions. This gives me the best of both worlds: server-side data fetching for performance and SEO, plus rich client-side interactivity."

**Q: "How do you optimize performance in Next.js?"**

**A:** "I use several strategies:

1. **Static Generation** - Pre-render pages at build time for instant loads
2. **Server Components** - Eliminate client JavaScript for data fetching
3. **Code Splitting** - Dynamic imports for modals and heavy components
4. **Image Optimization** - Next.js Image component with lazy loading
5. **Data Enrichment** - Transform normalized data at build time, not runtime

In my project, I reduced bundle size by 85KB by moving data fetching to Server Components and using a Map-based enrichment pattern that's O(n+m) instead of O(n×m)."

**Q: "Explain a time you debugged a complex build issue."**

**A:** "I encountered a webpack error where Node.js modules were being bundled for the browser. The root cause was importing a file using fs/path into a component that eventually got imported by a Client Component.

I solved it by:

1. Understanding the import chain through error messages
2. Recognizing the Server/Client boundary issue
3. Refactoring the enrichment function to be pure (no Node.js imports)
4. Properly separating Server Components (data fetching) from Client Components (interactivity)

This taught me the importance of understanding bundler behavior and component boundaries in modern React frameworks."
